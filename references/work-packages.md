# Work packages: splitting the plan so people and agents do not collide

Use this in Phase 5. Contents: 1 Goal, 2 Building packages, 3 File ownership, 4 Shared hotspots in an EF code-first repo, 5 Dependencies and merge order, 6 Task brief template, 7 Limits to state.

## 1. Goal

Each package is a unit of work one developer or coding agent can complete, review and merge with minimal conflicts. The plan should make it obvious which files each package may touch, so assigning two packages to two people is safe.

## 2. Building packages

1. Start from `profile.json`: the connected table groups (tables linked by shared workflows) and the workflows per table.
2. Put proposals that touch the same table, or the same service or repository, in the **same package**. Two people editing the same service is the commonest source of conflicts.
3. Proposals in different connected groups, with no shared service or file, can go in different packages and run in parallel.
4. A **hub table** (one used by a large share of workflows) cannot be split cleanly across packages. Make it its own package, scheduled first or done by one owner, and let others depend on it.
5. Keep packages a reviewable size (a few days of work). Split a large group by proposal type: indexes first, then service query fixes, then table splits.
6. Always create a **PKG-00 Foundation / Integration** package. It owns the shared hotspots (section 4): feature flag infrastructure, shared abstractions, DI registration, and the migrations. Other packages depend on it and never edit those files.
7. Name packages by functionality (for example "Orders read path", "Customer profile split"), not by person.

## 3. File ownership

For every package list, in separate cells:

- **Controllers affected (unchanged, read-only):** shown so reviewers see the blast radius and confirm nothing changes there.
- **Existing services/repositories referenced (read-only):** what the new code mirrors or calls.
- **New files to create:** full paths under a package-specific folder, for example `src/Data/Optimization/PKG-03/...` and `src/Services/Optimization/PKG-03/...`. Agents add files only inside their own folder.
- **Existing files to modify:** ideally empty. Anything listed here is a conflict risk and should belong to PKG-00 or be a single-owner exception with a reason.

Separate file paths with `;` in table cells. The export script flags any path that appears in two packages' lists.

## 4. Shared hotspots in an EF code-first repo

Assign each to exactly one owner package (usually PKG-00). Other packages treat them as read-only.

| Hotspot | Why it conflicts | Rule |
|---|---|---|
| `*ModelSnapshot.cs` and the `Migrations/` folder | Every migration rewrites the snapshot; two parallel migrations conflict | Packages write entities and configurations only. PKG-00 generates migrations one at a time in merge order |
| `DbContext` (new `DbSet`s, `OnModelCreating`) | Every new entity adds lines here | Prefer one new `IEntityTypeConfiguration` per package picked up by `ApplyConfigurationsFromAssembly`, so the context changes once. If a second `DbContext` is used for new tables, PKG-00 creates it |
| DI registration (`Program.cs`, service collection extensions) | Every new service adds a line | Each package ships its own registration extension class; PKG-00 calls them once, behind the feature flag |
| Feature flag and configuration (`appsettings*.json`, flag classes) | Same file edited by many | PKG-00 defines one flag per package up front |
| Shared base classes, generic repositories, mappers (AutoMapper profiles), result wrappers | Changes ripple to everyone | Read-only; request changes through PKG-00 |
| Test fixtures, shared test helpers, seed data | Many tests depend on them | PKG-00 owns; packages add their own test files |
| Existing interfaces the controllers use | Signature changes break the API layer | Frozen; new services implement the existing interface |

## 5. Dependencies and merge order

- State `Depends on` per package (for example everything depends on PKG-00's flag infrastructure; a split package depends on the index package for the same table if the split reuses it).
- Produce a **merge order**: PKG-00 foundation first, then independent packages in any order, then packages that depend on earlier ones. Migrations are generated by PKG-00 in that same order, right before or as each package merges.
- Call out sequencing for the data migration: backfill jobs run after the migration that creates the tables and before the flag flips.
- Note what can run in parallel (a batch number or "wave" per package).

## 6. Task brief template (one per package, ready to hand off)

```markdown
### PKG-03 brief: <name>
Goal: <one sentence>
Proposals: PROP-005, PROP-006
Do not touch: controllers, existing services/entities/migrations, shared hotspots (owned by PKG-00).
Create only under: <paths>
Steps: 1) ... 2) ... 3) ...
Data migration: <backfill + sync + validation summary, link to the migration table row>
Tests required: <contract/characterization tests proving identical responses; migration validation tests>
Definition of done: <checklist, including rollback rehearsal and flag defaulting to old service>
Rollback: flip flag <name> to old service; <any data note>
Depends on: PKG-00 (flag infrastructure)
```

## 7. Limits to state in the plan

- File lists come from the audit's traces and the code reading in this plan. Hidden shared helpers can be missed, so ask the implementer to run a quick overlap check (the plan's `File_Overlap` sheet, plus a repo search for the classes involved) before starting.
- Packages reduce conflicts, they do not remove them. The foundation package and merge order matter more than the split itself.
- Tightly coupled tables may force fewer, larger packages than hoped. Say so and explain which table coupling causes it.
